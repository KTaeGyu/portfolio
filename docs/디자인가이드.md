# 디자인 가이드

지금 화면이 단순한 것은 **뼈대만 세웠기 때문이 아니라, 정해 둔 값이 없기 때문**이다.
글씨 크기가 몇 단계인지 · 여백이 무엇의 배수인지 · 강조를 무엇으로 하는지가 없으면
요소를 아무리 더해도 더 채워질 뿐 더 좋아지지 않는다. 이 문서는 그 값을 정한다.

조사한 자료는 맨 아래 「참고」에 있다.

---

## 1. 이 사이트가 이겨야 할 조건

이직용이라 독자는 채용 담당자 한 종류다. 자료가 공통으로 말하는 것은 셋이다.

| 조건 | 근거 |
|---|---|
| **첫 화면에서 상위 3개 프로젝트가 역할·스택과 함께 보인다** | 첫 방문에 쓰는 시간이 30초 미만이다 |
| **메일 주소를 10초 안에 찾는다** | 못 찾으면 그냥 나간다 |
| **성과는 숫자로 말한다** | 「백엔드 성능 개선」보다 「p95 800ms → 120ms」가 이긴다 |

지금 화면은 셋 다 못 지킨다. 첫 화면이 소개글로 다 차서 프로젝트가 한 개도 안 보이고,
메일은 히어로에 작게 한 번 · 맨 아래 한 번뿐이고, 수치 자리는 비어 있다.
**「단순하다」의 절반은 디자인이 아니라 이 구조 문제다.**

---

## 2. 진단 — 지금 무엇이 비어 있나

| 증상 | 원인 |
|---|---|
| 화면이 평평하다 | 글씨 크기가 사실상 3단계뿐이고, 굵기·색으로만 구분한다 |
| 카드가 종이처럼 보인다 | 테두리 1px + 옅은 그림자 하나. 카드끼리 위계가 없다 |
| 스크롤이 지루하다 | 구역 구분이 가로선 하나뿐이고 리듬이 없다 |
| 첫인상이 없다 | 히어로에 이름과 문단만 있다. 눈이 멈출 곳이 없다 |
| 여백이 들쭉날쭉하다 | `3.5rem` · `1.25rem` · `0.85rem` 처럼 근거 없는 값이 섞여 있다 |

---

## 3. 정할 값

### 3-1. 간격 — 8의 배수만 쓴다

모든 여백을 8px 배수로 잡는다. 안쪽 여백(padding)은 바깥 여백(margin)보다 **작거나 같게** 둔다 —
이것만 지켜도 요소가 서로 붙었는지 떨어졌는지가 눈에 바로 보인다.

```
--space-1: 0.5rem   (8px)   요소 안 촘촘한 틈
--space-2: 1rem     (16px)  줄 사이
--space-3: 1.5rem   (24px)  카드 안쪽 여백
--space-4: 2rem     (32px)  묶음 사이
--space-6: 3rem     (48px)  구역 안 큰 구분
--space-8: 4rem     (64px)  구역 사이
--space-12: 6rem    (96px)  히어로 위아래
```

지금 CSS 의 `3.5rem` · `2.25rem` · `1.75rem` 같은 값은 전부 이 사다리 위의 값으로 바꾼다.

### 3-2. 글씨 — 6단계, 비율 1.5

단계가 적으면 평평하고, 많으면 지저분하다. **여섯 단계로 고정**하고 그 밖의 크기는 쓰지 않는다.

| 이름 | 크기 | 쓰는 곳 |
|---|---|---|
| `display` | `clamp(2.5rem, 7vw, 4.5rem)` | 이름 하나뿐 |
| `title` | `1.75rem` | 구역 제목 |
| `heading` | `1.25rem` | 카드 제목 · 회사명 |
| `body` | `1rem` | 본문 |
| `small` | `0.875rem` | 메타 정보(기간·역할) |
| `label` | `0.75rem` | 태그 · 구역 머리말 |

지금은 `display` 가 최대 3.4rem 이고 `title` 이 0.8rem 이라 **제목이 본문보다 작다.**
구역 제목을 대문자 라벨로만 처리한 것이 화면을 평평하게 만든 가장 큰 원인이다.

- 본문 줄 길이는 **한 줄 45~75자**. 지금 `44rem` 은 한글 기준으로 너무 길다 → `38rem`
- 줄간격은 본문 1.7, 제목 1.2. 큰 글씨일수록 좁게
- 숫자에는 `font-variant-numeric: tabular-nums` (이미 들어 있음, 유지)

### 3-3. 색 — 무채색 + 강조 하나

자료가 공통으로 짚는 2026년 개발자 포트폴리오의 기본값은 **색을 거의 빼는 것**이다.
검정·흰색·회색으로 가고 강조색은 하나만 둔다. 지금 구조(토큰 한 벌)는 그대로 맞으니
**바꿀 것은 대비뿐**이다.

- 배경을 두 겹으로 나눈다 — `--bg`(페이지) / `--surface`(카드). 지금은 거의 같은 색이라 카드가 안 뜬다
- 텍스트는 세 단계(`--text` / `--text-dim` / `--text-faint`)를 지키되, 본문 대비를 WCAG AA(4.5:1) 위로
- 강조색은 **링크 · 태그 · 수치 세 곳에만**. 지금처럼 소제목까지 강조색을 쓰면 강조가 사라진다

### 3-4. 히어로 — 눈이 멈출 곳을 만든다

자료의 사례는 둘로 갈린다. **영상·파티클 같은 배경 연출**이거나, **단색 위의 강한 한 문장**이다.
후자를 고른다 — 가볍고, 로컬 폰트만으로 되고, 첫 화면 로딩을 늦추지 않는다.

- 이름을 `display` 로 크게. 지금보다 한 단계 더 크게 가도 된다
- 그 아래 **한 문장**만 남기고 소개 문단은 접는다(또는 경력 구역으로 내린다)
- 히어로 바닥에 **핵심 수치 3개를 가로로** 둔다 — 「연계 시스템 n개 · 무중단 전환 5대 · 경력 n년」
  30초 안에 읽히는 것은 문단이 아니라 이 줄이다
- 메일 주소는 **버튼 모양으로** 히어로 안에 둔다. 텍스트 링크로는 10초 안에 안 걸린다

### 3-5. 프로젝트 — 카드는 유지, 위계를 넣는다

3~6개를 「무엇을·왜」 한 줄 + 링크와 함께 보이는 것이 표준이고, 지금 카드 구조가 이미 그 모양이다.
바꿀 것은 **전부 같은 무게로 보인다**는 점 하나다.

- **위 2개는 가로 전면(1열), 나머지는 2열**. 순서가 곧 중요도라는 것을 눈으로 보여준다
- 수치 블록을 **한 줄 요약 바로 아래로** 올린다. 지금은 메타 정보 뒤에 있어 스캔에 안 걸린다
- 수치가 없는 카드는 그 자리를 비우지 말고 **한 줄 요약을 크게** 써서 높이를 맞춘다
  (지금 SSO 카드에 빈 공간이 크게 남는 이유)
- 호버에 반응 하나 — 테두리를 강조색으로, 그림자를 한 단계. 그 이상은 넣지 않는다

### 3-6. 움직임 — 두 가지만

자료가 경고하는 것은 **초기 렌더를 늦추는 무거운 애니메이션**이다. 1초 안에 내용이 보여야 한다.

- 스크롤 진입 시 **구역 단위 페이드 업**(150ms, 한 번만). CSS `animation-timeline` 또는 IntersectionObserver
- 호버 전이 120ms
- `prefers-reduced-motion` 에서 둘 다 끈다 (이미 스크롤 동작은 처리해 둠)

### 3-7. 반응형

- 카드 격자: 1열(~640px) / 2열(~1024px) / 위 2개 전면 + 2열(1024px~)
- 글씨는 `clamp()` 로 흐르게. 브레이크포인트에서 튀지 않게
- 누르는 것은 최소 44×44px

---

### 3-8. 구역 순서

**프로젝트 → 경력 → 소개 → 기술 → 연락처.** 채용 담당자가 먼저 보는 것은 경력 연혁이 아니라
무엇을 만들었는가다. 경력이 앞에 있으면 프로젝트가 세 번째 화면으로 밀린다.

§4-1 의 표준은 소개(About)를 프로젝트 **앞**에 둔다. 여기서는 뒤로 뺐다 —
앞에 두면 §1 의 「첫 화면에서 상위 3개 프로젝트가 보인다」가 깨진다.
배경 이야기는 프로젝트를 보고 관심이 생긴 다음에 읽는 것이다.

상단에 **고정 네비게이션**을 둔다. 한 장 스크롤에서 구역이 다섯을 넘으면
스크롤 말고 다른 이동 수단이 있어야 한다.

## 4. 구성 — 풀스택 포트폴리오의 표준

조사한 자료들이 거의 같은 뼈대를 말한다. 우리 구성이 어디까지 맞고 어디가 빈지 대조해 둔다.

### 4-1. 표준 순서

| # | 구역 | 우리 |
|---|---|---|
| 1 | 히어로 — 이름 + 무엇을 하는 사람인가 | 있음 |
| 2 | **네비게이션(상단 고정)** | **없음** |
| 3 | **About — 배경 · 학력 · 자격증** | **없음**(히어로 요약이 대신) |
| 4 | 프로젝트 **3~5개** | 6개 — 하나 넘는다 |
| 5 | 기술 — 언어 / 도구 / 프레임워크로 쪼갬 | 있음 |
| 6 | 경력 | 있음 |
| 7 | 블로그 | 없음(선택 항목) |
| 8 | 연락처 | 있음 |

기술 구역에 대한 공통 조언이 하나 더 있다 — **지금도 쓰고 싶은 것만 적는다.**
할 줄 아는 것을 다 적으면 하기 싫은 일이 들어온다.

### 4-2. 풀스택만의 요구

다른 직군과 갈리는 지점이 분명하다.

- **앞단과 뒷단을 각각 명시적으로** — 프론트는 반응형 · 접근성 · 성능, 백은 API 설계 · DB 선택 · 확장성
- **아키텍처 다이어그램** — 프론트가 백과 어떻게 통신하고 데이터가 어디로 흐르는지. 자료마다 반복해서 나온다
- **트레이드오프를 말로** — NoSQL vs SQL, 도커 vs 서버리스처럼 **왜 그것을 골랐는가**
- **라이브 데모 + GitHub 링크** — 열어볼 수 있어야 한다

### 4-3. 프로젝트 한 건의 골격

**문제 → 내 역할 → 접근(아키텍처 · 기술 선택) → 결과(수치)** 넷.
수치는 **지연시간 · 처리량 · 가동률 · 비용**을 지목한다. 그리고 **결과를 맨 위로** 올린다.

지금 카드의 `points` 는 대부분 「문제」와 「접근」이고 **「결과」 칸이 통째로 비어 있다**(전부 `TODO`).
자료가 가장 강조하는 칸이 그 칸이다.

### 4-4. 회사 일을 싣는 법 — 지금 방식이 표준이다

UI 가 없는 백엔드 · 인프라 일과, 공개할 수 없는 회사 일에 대한 답이 명확하다.

- **익명화한다.** 「이커머스, 하루 5천만 요청」처럼 **맥락과 규모만** 남기고 내부는 뺀다
- **픽셀이 아니라 「생각과 영향」을 보인다** — 다이어그램 · 결정의 근거 · API 설계 노트

「대학 행정 시스템」식으로 일반화한 지금 방식이 바로 이것이다. 방향은 맞다.

### 4-5. 벌어진 곳 세 군데

| 격차 | 무게 |
|---|---|
| **아키텍처 다이어그램 0개** | 🔴 UI 없는 일을 보이는 사실상 유일한 수단인데, 우리 프로젝트는 대부분 그런 일이다 |
| **네비게이션 없음** | 🔴 페이지가 길어졌는데 이동 수단이 스크롤뿐이다 |
| **결과(수치)가 전부 TODO** | 🔴 자료가 가장 강조하는 칸이 비어 있다 |
| About 구역 없음 | 학력 · 자격증 자리가 없다 |
| 라이브 데모 | 회사 일은 구조적으로 불가. the-gang 만 가능하다 |

---

## 5. 하지 않을 것

- **글래스모피즘 · 그라데이션 범벅.** 유행이지만 이 사이트의 독자는 읽으러 온다
- **터미널 흉내 · 코드 에디터 흉내.** 사례에 있긴 하나 내용을 읽기 어렵게 만든다
- **영상 배경 · 파티클.** 첫 화면 로딩을 늦춘다
- **프로젝트 20개.** 3~6개가 이긴다. 지금 6개는 상한이다
- **다크/라이트 토글 버튼.** 시스템 설정을 따르는 지금 방식으로 충분하다

---

## 6. 적용 순서

| 순서 | 무엇 | 얻는 것 | 공수 |
|---|---|---|---|
| 1 | 토큰(간격·글씨) 정의하고 기존 값 치환 | 화면 전체 리듬. **효과가 가장 크다** | 0.5일 |
| 2 | 히어로 재구성(수치 줄 · 메일 버튼) | 30초·10초 조건을 지킨다 | 0.5일 |
| 3 | 구역 제목 위계 · 대비 조정 | 평평함이 사라진다 | 0.3일 |
| 4 | 카드 위계(전면 2 + 격자) · 수치 위로 | 스캔이 된다 | 0.5일 |
| 5 | 움직임 둘 | 완성도. **없어도 되는 항목** | 0.3일 |

1~3 까지만 해도 「단순하다」는 대부분 사라진다. 4는 프로젝트 내용이 채워진 뒤가 낫고,
5는 굳이에 가깝다.
